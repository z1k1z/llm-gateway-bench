# Стенд для сравнения self-hosted LLM-гейтвеев

Замеряет LiteLLM, Bifrost и new-api в трёх конфигурациях на одном сервере:
оверхед, TTFT на стриминге, поведение при отказах апстрима и состояние
безопасности «из коробки».

Главная измеряемая величина — не «какой гейтвей быстрее», а насколько
меняются числа одного и того же гейтвея между профилями `bare`, `prod`
и `keys`. Публичные бенчмарки гейтвеев сняты в профиле `bare`, где
логирование, учёт расходов и персистентность отключены — то есть ровно то,
за чем гейтвей и ставят.

## Что нужно на сервере

- Linux, docker (compose не нужен — стенд работает на `docker run`)
- `curl`, `jq`, `awk`, `python3` — для скриптов
- `nmap` — только для блока безопасности
- выход в интернет для скачивания образов

Профилей больше одного, поэтому гейтвеи поднимаются **по одному**: все
контейнеры работают в host-сети и делят порты хоста.

## Порты

| Что | Порт |
|---|---|
| mock-a (основной апстрим) | 9000 |
| mock-b (резервный, для фолбэка) | 9010 |
| LiteLLM | 4000 |
| Bifrost | 8080 |
| new-api | 3000 |
| Postgres для LiteLLM | 55432 |

## Быстрый старт

```bash
# один раз: прайсинг для Bifrost (без него он не стартует)
./gateways/bifrost/offline/fetch.sh

# сеть, образы, мок-апстримы
./run.sh prepare

# контрольная группа: напрямую в мок, без гейтвея
./run.sh control
# потолок самого стенда: без него числа пропускной способности не публикуем
./run.sh saturate

# один гейтвей в одном профиле
./run.sh up    bifrost bare
./run.sh bench bifrost bare
./run.sh faults bifrost          # 429, 503, таймаут, обрыв стрима
./run.sh fallback bifrost        # сам поднимает профиль fallback
./run.sh security bifrost bare
./run.sh down  bifrost

# или всё сразу по трём гейтвеям в одном профиле
./run.sh all bare
./run.sh all prod
./run.sh all keys

# собрать таблицы
./run.sh report
```

Результаты — в `results/`. Их и надо прислать целиком.

## Профили

| Профиль | Что включено | Зачем |
|---|---|---|
| `bare` | только проксирование | воспроизводит условия вендорских бенчмарков |
| `prod` | журнал запросов и учёт расходов в своей БД | то, за чем гейтвей ставят |
| `keys` | то же плюс виртуальные ключи с лимитом бюджета | раздача доступа командам |
| `fallback` | два апстрима, при отказе первого запрос уходит во второй | только для `./run.sh fallback` |

Ключи клиента. В `bare` и `prod` LiteLLM получает мастер-ключ, в `keys` —
виртуальный ключ `BENCH_VK` с бюджетом, его заводит `run.sh up` через
`/key/generate`. Bifrost с `config_store` (prod, keys, fallback) без
виртуального ключа инференс не пускает, поэтому ему `BENCH_VK` нужен везде,
кроме `bare`; без хранилища он принимает запросы вообще без ключа. new-api
всегда работает со своим токеном из `seed.sh`, режимов без учёта у него нет.

У моделей мока нет цены в каталогах, поэтому цена задана явно: в
`config.keys.yaml` у LiteLLM и в `pricing_overrides` у Bifrost,
1 и 2 доллара за миллион входных и выходных токенов.

«Одинакового `bare`» у трёх гейтвеев не существует: у LiteLLM учёт появляется
только с `DATABASE_URL`, у Bifrost выключается через `client.enable_logging`
и отключение сторов, а у new-api учёт расходов — смысл продукта. Это
расхождение само по себе результат и оговаривается в статье.

## Мок-апстрим

Профиль задаётся **именем модели**, а не заголовком: имя модели доходит через
любой гейтвей, кастомные заголовки — нет.

| Модель | TTFT | На токен | Токенов | Полное время |
|---|---|---|---|---|
| `mock-fast` | 20 мс | 2 мс | 64 | ~148 мс |
| `mock-realistic` | 400 мс | 33 мс | 150 | ~5,35 с |

Отказы включаются на ходу и применяются детерминированно, каждый N-й запрос:

```bash
curl -X POST http://127.0.0.1:9000/control -d '{"mode":"503","rate":0.25}'
curl -X POST http://127.0.0.1:9000/control -d '{"mode":"none"}'
```

Режимы: `none`, `429`, `503`, `timeout` (спит дольше любого таймаута),
`truncate` (обрывает стрим на половине токенов, без `finish_reason` и `[DONE]`).

Каждый ответ получает уникальный `id`. С постоянным id LiteLLM складывал все
успешные запросы в одну строку `SpendLogs`, и нагрузка на учёт исчезала.

## Почему харнесс свой

`curl -w '%{time_starttransfer}'` и обычные нагрузчики срабатывают на
заголовках ответа, а не на первом токене. На моке это даёт TTFT 0,5 мс при
настроенных 20 мс. TTFT измеряется только разбором SSE на стороне клиента,
поэтому харнесс считает время до первого **непустого** `delta.content`.

Каждый замер повторяется несколько раз, в отчёт идёт медиана и разброс
min–max. Одиночные прогоны не публикуем.

Настройки через переменные окружения:

```bash
CONC=8 CONC_HI=64 REQS=120 REPEATS=5 REQS_SLOW=48 REPEATS_SLOW=3 ./run.sh all bare
```

Модель нагрузки закрытая: `CONC_HI` клиентов шлют запросы друг за другом.
При ответе ~160 мс потолок такой нагрузки — около `CONC_HI / 0,16` rps,
поэтому при `CONC_HI=64` Go-гейтвеи упираются в мок, а не в процессор
(на стенде: контроль 304 rps, Bifrost 298, CPU 36–55%). Чтобы нагрузить
гейтвей, `CONC_HI` поднимают и сверяют с `saturate`.

## Настройка new-api

new-api без администратора, канала и токена не принимает запросы. Мастер
первого запуска делает это в браузере, но всё доступно и через его HTTP API:
`./run.sh up newapi` сам вызывает `gateways/newapi/seed.sh`. Пароль
администратора генерируется и лежит в `gateways/newapi/data/admin.txt`,
токен для замеров — в `data/api-key.txt`. Ручной путь и шаг со скриншотом
для статьи — в `gateways/newapi/seed.md`.

## Ядра и воркеры

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `GW_CPUS` | не задана | cpuset для всех гейтвеев, например `0-3`. Нужна, когда гейтвей и нагрузчик на одной машине |
| `LITELLM_WORKERS` | число ядер из `GW_CPUS` или `nproc` | из коробки LiteLLM стартует один воркер; документация для VM советует по числу vCPU |

На VDS ничего задавать не нужно: гейтвей на сервере один, нагрузчик на втором.

## Маркеры для поиска утечек

В `sentinels.env` лежат два намеренно нетипичных значения:

- `UPSTREAM_KEY` — ключ, который гейтвей отдаёт апстриму;
- `MASTER_KEY` — ключ, которым клиент обращается к гейтвею.

Блок безопасности ищет их в логах контейнера и в дампе БД. Ноль попаданий
означает, что в этом месте секрет не лежит открытым. Значения ненастоящие
и существуют только внутри стенда.

## Что не входит в стенд

- Rust-ветка LiteLLM: готового образа нет, собирается из исходников,
  и на `/chat/completions` со стримингом не участвует. Разбирается в статье
  отдельно.
- Portkey Gateway: запускается через `npx`, последний коммит в OSS-репозитории
  25.05.2026. Проверяется отдельно, в сравнение не ставится.
- Plano: дата-плейн для оркестрации агентов на Envoy, со своей моделью
  роутинга, которая хостится вендором. Другой класс задач.
